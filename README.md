# SIS — Formal Verification of Smart Irrigation Systems

Reproducibility artefact for the paper

> **A formal verification framework for smart irrigation systems under
> weather uncertainty using probabilistic model checking**
> Sobia Ashraf, Osman Hasan, Sa'ed Abed.
> Submitted to *Smart Agricultural Technology*.

This repository contains the PRISM/Storm models, property files,
experiment driver scripts, raw and parsed results, and analysis
utilities used to produce the tables and figures in the paper.

```bash
git clone https://github.com/SobiaatNUST/smart-irrigation-verification.git
```

> **Scope note.** Every paper table, figure, and numeric value can now
> be checked from committed data — deterministic baselines, MO1 named
> policies **and θ-sweep**, MO2 budget sweep, MO3 grid, MO4 grid, the
> sensitivity sweep, and the **scheduler operating points + policy
> heatmap** (`tab:moschedulers`, `fig:policyheatmaps`). The only files
> not committed are the **raw scheduler lookup tables**
> (`.scheduler` ≈158 MB each, `.states` ≈1.3 GB) — these exceed
> GitHub's size limits and are regenerated by the provided scripts.
> See the **traceability matrix** in
> [`REPRODUCIBILITY.md`](REPRODUCIBILITY.md).

## 1. Project overview

The paper formalises a smart-irrigation system as a Markov decision
process (MDP) over four environmental modules (weather forecast,
evapotranspiration, precipitation error, soil dynamics) with a
pluggable controller interface, and evaluates three reference
controllers under exhaustive PCTL verification:

- **M1** — open-loop Shang formula (baseline)
- **M2** — five-zone threshold heuristic (closed-loop)
- **M3** — nondeterministic action abstraction whose deployable policy
  is obtained via Storm multi-objective synthesis

### Multi-objective query numbering (important)

The paper labels four multi-objective queries **MO1–MO4**. Some
**internal file/label names predate the paper numbering** (e.g. the
property tag `phi_mo4` and file prefix `mo4_` inside
`results/mo3/`). Use this mapping:

| Paper | Meaning | Query | Repo location |
|-------|---------|-------|---------------|
| **MO1** | Min water s.t. safety ≥ θ | `multi(R{"water_usage"}min=? [C<=140], P>=θ [G "safe"])` | `results/mo1/` |
| **MO2** | Max safety s.t. water ≤ B | `multi(Pmax=? [G "safe"], R{"water_usage"}<=B [C<=140])` | regenerate (`run_mo2_budget_sweep.sh`) |
| **MO3** | Min violations s.t. water ≤ B | `multi(R{"safety_violations"}min=? [C<=140], R{"water_usage"}<=B [C<=140])` | `results/mo3/` (rows tagged `phi_mo4`/`mo4_*` — legacy tag) |
| **MO4** | Min water s.t. violations ≤ V | `multi(R{"water_usage"}min=? [C<=140], R{"safety_violations"}<=V [C<=140])` | regenerate (`run_mo4_grid.sh`) |

Principal findings reproducible from this repo: **M2 strictly
dominates M1**, **M3 saves 43–66 % water vs M2** under the same
certified safety guarantee, and the two-axis Pareto geometry exposes a
soil-class infeasibility ceiling.

## 3. Requirements

| Tool       | Version              | Notes |
|------------|----------------------|-------|
| **Storm**  | 1.13.0 (≥ 1.9 works) | Reference version for the paper. Build/use with the multi-objective backend enabled; sparse engine. |
| **PRISM**  | 4.8.x                | Optional; used for cross-checking M2 single-objective queries. |
| **Python** | ≥ 3.10               | Analysis/parsing utilities — **standard library only**, no third-party packages. |
| **bash**   | ≥ 4.0                | Driver scripts. |

> The committed result files were generated on Apple-silicon/Linux
> hosts with Storm in the 1.9–1.12 range; any Storm ≥ 1.9 with
> multi-objective support reproduces the same values (timings will
> differ by host and Storm version). See `requirements.txt`.

**Configure your Storm binary** once per session by editing the
`STORM_BIN` line near the top of each `scripts/*.sh`, or by passing
`--storm /path/to/storm` where the script accepts it.

## 4. Reproduction quick start

All commands assume the **repo root** as the working directory. The
driver scripts now reference the models and properties by their
in-repo paths (`../models/...`, `../properties/...`), so no file
renaming is needed.

```bash
# 1. Deterministic baselines  -> Table 5 (tab:det)  [minutes]
bash scripts/M1_run.sh   --storm /path/to/storm
bash scripts/M2_run.sh   --storm /path/to/storm

# 2. MO1 named policies  -> Table 6 (tab:pareto), Fig. 8 (fig:m3namedheat)  [~hours/cell]
bash scripts/run_mo1_tier1_named.sh --storm /path/to/storm --parallel 4

# 3. MO1 theta sweep  -> Fig. 10 (fig:pareto), Fig. 9 (fig:m3pareto)
bash scripts/run_mo1_theta_sweep.sh 0.025

# 4. MO2 budget sweep -> Table 7 (tab:budget_pareto), Fig. 11 (fig:budget_pareto)
bash scripts/run_mo2_budget_sweep.sh 0.025

# 5. MO3 grid -> Fig. 12 (fig:mo3feas)
bash scripts/run_mo3_grid.sh --storm /path/to/storm
python analysis/analysis_scripts/analyze_mo3_grid.py

# 6. MO4 grid -> Fig. 13 (fig:mo4heat)
bash scripts/run_mo4_grid.sh --storm /path/to/storm

# 7. Scheduler export (deployable lookup tables) -> Table 9 (tab:moschedulers)
bash scripts/scheduler_exports/run_sched_export_mo1.sh --storm /path/to/storm
# ... mo2, mo3, mo4 analogously

# Parse any raw Storm .txt directory into a tidy CSV
python scripts/utilities/parse_storm_output.py <input_dir> <output.csv>
```

Figure numbers above are indicative; the authoritative mapping (paper
item → script → data → status) is in
[`REPRODUCIBILITY.md`](REPRODUCIBILITY.md).

> **Figures are not auto-plotted.** All paper figures are drawn in
> LaTeX/TikZ directly from the CSV/`.txt` values. Regenerating a
> figure means re-running the experiment, reading the numbers from the
> parsed CSV, and (for the camera-ready) updating the corresponding
> TikZ/pgfplots block. `analyze_mo3_grid.py` is the only figure-support
> script (it prints the MO3 feasibility-budget summary behind
> `fig:mo3feas`).

## 6. Known limitations / not included

- **Raw scheduler lookup tables** (`.scheduler` ≈158 MB each;
  `g3_*.states` ≈1.3 GB) are the **only** files not committed — they
  exceed GitHub's size limits. Their *operating-point results and
  metadata* (which back `tab:moschedulers`) and the rendered
  `figures/policy_heatmaps.pdf` (= `fig:policyheatmaps`) **are**
  committed. Regenerate the full tables with
  `scripts/scheduler_exports/run_sched_export_mo*.sh`
  (see `results/scheduler_exports/README.md`).
- Figures require a manual data → TikZ transcription step (see §4),
  except `fig:policyheatmaps`, which is produced directly by
  `analysis/analysis_scripts/plot_policy_heatmaps.py`.
- Internal property/file tags use **legacy MO numbering** that is
  shifted relative to the paper: `results/mo3/` rows are tagged
  `phi_mo4`/`mo4_*` (= paper MO3), `results/mo4/` rows are tagged
  `phi_mo2`/`mo2_*` (= paper MO4), and `results/mo2/` comes from the
  "G1 budget sweep" (= paper MO2). See the mapping in §1.
